# Runtime-контур: чего сейчас нет и что предполагается дальше

Этот документ описывает **следующую** итерацию. Ничего из перечисленного здесь
PKO сегодня не делает, и ни одно требование этого документа не должно читаться
как возможность текущей версии.

## Почему одного анализатора недостаточно

PKO восстанавливает объекты управления из кода и выпускает запись допуска
`BASIC_RECORD`. Этого хватает, чтобы ответить на вопрос «можно ли запускать
пилот». На вопрос «соблюдается ли ограничение при каждом действии» статический
разбор ответить не может: наличие таймаута в коде не доказывает, что он
применяется перед вызовом, а наличие обработки ошибок — что это fallback по
смыслу стандарта.

Поэтому в `src/pko/standard/catalog.py` такие требования помечены
`NEEDS_RUNTIME`, а не `NOT_CHECKED`. Разница принципиальна: `NOT_CHECKED` —
работа, которую можно сделать; `NEEDS_RUNTIME` — граница подхода.

## Схема исполнения

```text
business_intent + версия кода + отчёт тестов
                 ↓
             BASIC Gate  ← это PKO делает сегодня
                 ↓
        разрешённый scope и режим
                 ↓
запрос → план → выбор операции → policy layer → исполнитель
                                     ↓
                    ALLOW / DENY / CONFIRM / HANDOFF / SAFE_STOP
                                     ↓
                       append-only журнал исполнения
```

Ключевой переход — между четвёртой и пятой строкой. Модель не вызывает SQL,
HTTP или Python: она формирует `ActionProposal` с идентификатором операции из
каталога, а решение принимает детерминированный слой.

## Контракты

Формы описаны в `src/pko/model/resources.py`. Модуль состоит из одних
определений: ни исполнения, ни хранилища в нём нет, и его импорт ничего не
включает.

| Ресурс | Отвечает на вопрос |
|---|---|
| `ActionProposal` | что модель предлагает сделать |
| `PolicyDecision` | разрешено ли это и на каком основании |
| `Confirmation` | кто и когда подтвердил действие |
| `Handoff` | почему управление передано человеку |
| `ExecutionEvent` | неизменяемая запись шага |
| `ExecutionRecord` | минимальная запись запуска §8.0.2 |

## Решения следующей итерации

- **Хранилище** — SQLite или JSONL внутри каталога результата PKO. Внешней
  инфраструктуры не требуется, журнал переносится вместе с отчётом.
- **Подтверждение и handoff** — локальный CLI или экран PKO. Ни почты, ни
  внешних систем: подтверждение должно работать там же, где идёт прогон.
- **Журнал** — только дополняется. Правка задним числом обесценивает его как
  доказательство.

## Чего эта итерация не даёт

- Ни одно ограничение не применяется во время исполнения.
- Ни одно действие не проходит через policy layer.
- Журнала исполнения не существует, и его отсутствие не означает, что действий
  не было — только что их нельзя подтвердить.

Пока это так, профиль FULL в отчёте означает «промышленные требования §6
применяются», а не «выполнены». Именно это различие показывает раздел
«Готовность к промышленному контуру» в `index.html` и файл
`full_readiness.json`.
