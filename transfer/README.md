# Перенос изменений

Каталог для переноса PKO на другой компьютер — например, на корпоративный, где
есть доступ к внутреннему Bitbucket и внутренним endpoint'ам моделей.

Архивом (`CORPORATE_FIRST_RUN.md`) переносят PKO целиком — это нужно один раз,
при первой установке. Дальше переносят только изменения, двумя способами.

| Способ | Когда | Команда |
|---|---|---|
| **Каталог файлов** | у получателя обычная копия PKO без git | `make bundle` |
| **Патч** | у получателя git-дерево на том же базовом коммите | `make patch` |

Каталог проще: распаковал, скопировал поверх — готово. Патч строже: показывает
ровно строки изменений и отказывается применяться не к той версии.

## Каталог файлов (`make bundle`)

В `transfer/bundle/` собирается `files/` с той же структурой, что и
репозиторий, плюс опись и контрольные суммы:

```bash
make test            # переносить имеет смысл только зелёную версию
make bundle
tar -czf pko-изменения.tar.gz -C transfer bundle
```

На принимающей стороне:

```bash
tar -xzf pko-изменения.tar.gz
cd bundle
shasum -a 256 -c SHA256SUMS      # на Linux: sha256sum -c
cp -R files/. /path/to/pko/
cd /path/to/pko && make test
```

Копирование поверх не удаляет файлы. Если в этой версии что-то удалено,
`MANIFEST.md` перечислит такие пути отдельным разделом — их нужно убрать руками.

## Патч (`make patch`)

```bash
cd /path/to/pko
make test
make patch
```

В `transfer/out/` появятся три файла:

| Файл | Зачем |
|---|---|
| `pko-<дата>-<коммит>.patch` | сам патч |
| `pko-<дата>-<коммит>.patch.sha256` | контрольная сумма |
| `pko-<дата>-<коммит>.manifest.md` | базовый коммит, список файлов, инструкция |

Пометку в имени можно задать: `python3 transfer/make_patch.py --label отчёты`.

## Применить

На принимающей стороне нужен клон PKO на том же базовом коммите, который указан
в манифесте.

```bash
cd /path/to/pko
git rev-parse HEAD                  # должно совпасть с базовым коммитом
shasum -a 256 -c pko-…​.patch.sha256  # на Linux: sha256sum -c
git apply --check pko-….patch       # сухой прогон, ничего не меняет
git apply pko-….patch
make test
```

`git apply --check` отказал — значит дерево получателя отличается от базового.
Это не помеха, а сигнал: разберитесь с расхождением, а не применяйте патч с
`--3way` вслепую.

## Что в патч не попадает

Ключи и `.env`, кеши `~/.pko`, каталоги прогонов (`pko-out/`, `bench/runs/`),
генерируемые тестовые репозитории и материалы конкретного проекта
(`intent_ai_advisor*.yaml`, `business_requirements_ai_advisor.md`). Перечень
исключений — в `transfer/make_patch.py`, рядом с объяснением каждого пункта.

Перед записью патч просматривается на очевидные секреты: ключи вида `sk-…`,
приватные ключи, присваивания `api_key = "…"`. Находка прерывает сборку.
Проверка не доказывает отсутствия секретов — она ловит очевидное до отправки,
а решение принимает человек. Строки, где такой ключ является предметом теста
(`assertNotIn("sk-secret", …)`), сборку не блокируют.

## Границы

Патч переносит изменения относительно базового коммита, а не состояние целиком.
Если на принимающей стороне есть собственные правки тех же файлов, применение
не пройдёт — и это правильно: молча слить две версии PKO значит получить третью,
которую никто не проверял.
