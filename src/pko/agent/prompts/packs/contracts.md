## Пак: объявленные контракты

В репозитории найдена спецификация интерфейса, схема данных или манифест
инструментов. В таких системах интерфейс описан раньше кода, и по одному только
коду картина получается неполной.

Где искать: `openapi.yaml`, `swagger.json`, `api-spec.*`, файлы со схемами
(`$schema`, `"type": "object"` с `properties`), манифесты инструментов
(`tools.json`, `functions.yaml`, `*.manifest.*`), описания событий и очередей
(`asyncapi.*`, `events/*.json`), контракты gRPC (`*.proto`).

Как размечать:

- путь и метод из спецификации — `ENTRYPOINT` / `serve` / `http_server`;
- инструмент из манифеста — `STEP` / `call` / `agent_tool`;
- схема данных или события — `ARTIFACT` / `declare`;
- пороги и лимиты из конфигурации — `CONTROL` / `limit`, перечни — `allowlist`.

Главное правило пака: **объявление — не реализация**. Путь `POST /orders` в
спецификации доказывает, что интерфейс объявлен, и ничего не говорит о том,
существует ли обработчик. Поэтому:

1. Найдя объявление, ищи реализацию: обработчик маршрута, функцию инструмента,
   место, где схема читается. Нашёл — отметь **оба** наблюдения, реализацию со
   ссылкой на код.
2. Не нашёл — так и скажи в `claim`: «объявлен в спецификации, реализация не
   найдена». Это ценная находка, а не пробел в разведке: расхождение
   спецификации с кодом — материал для `CONTRADICTION`.
3. Наблюдение по одному файлу спецификации в решение о допуске не входит.
   Проверка «траектория восстанавливается из реализации» спрашивает про код.

Осторожно: сгенерированные клиенты и серверные заглушки (`generated/`, `_pb2.py`,
`*.gen.ts`) описывают тот же контракт второй раз. Отмечай контракт один раз — по
источнику, а не по каждому сгенерированному файлу.
