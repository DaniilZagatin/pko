## 0. Как читать документ

Документ восстановлен по реализации, а не написан до неё. Поэтому у каждого
требования указано происхождение:

| Метка | Значение |
|---|---|
| **[код]** | Поведение подтверждено реализацией, указан файл |
| **[ТЗ]** | Зафиксировано в `ТЗ v1` (`notebooks/*.xlsx`) |
| **[вывод]** | Логически следует из реализации, но прямо нигде не заявлено — **требует подтверждения владельца** |
| **[пробел]** | Требование, которого в реализации нет, но без него продукт не выводится за рамки PoC |

Всё, что помечено **[вывод]**, — это предложение, а не установленный факт.
Назначение продукта, целевые метрики и владельца результата из кода вывести
нельзя: их должен подтвердить бизнес-заказчик.

## 1. Бизнес-контекст и проблема

**Заказчик:** Департамент производственной системы Сбера и процессов (ДПСС) **[код]**
— роль агента прямо описана в системном промпте: «Ты — аналитик данных клиентских
путей (КП) и процессов департамента по процессам в Сбербанке (ДПССиП)»
(`app/services/step_configs/step0.py`).

**Проблема, которую решает продукт [вывод]:**

Редизайн клиентского пути или процесса в банке — это структурированная
методология из десяти шагов, которая сегодня выполняется вручную командой
аналитиков. Два узких места:

1. **Сбор входных данных.** Информация о процессе размазана по девяти
   разнородным системам (СберБуст, ПроМнение, Гемба, Голос территорий,
   SberBPM, ARIS и др.). Аналитик тратит значительную часть срока проекта на
   то, чтобы собрать и свести эти данные в единую картину.
2. **Соблюдение методологии.** Качество результата зависит от того, насколько
   строго аналитик следует методологии: формулировки Problem Statement по SMART,
   MECE-структура дерева гипотез, согласованность артефактов между шагами.
   Контроль этой согласованности сейчас ручной.

**Предлагаемое решение:** диалоговый ИИ-советник, который ведёт аналитика по
методологии шаг за шагом, автоматически подтягивает данные из систем-источников
по коду процесса и формирует на каждом шаге структурированный артефакт
установленного формата.

## 4. Границы решения

### В границах [код]

- Диалоговое сопровождение методологии редизайна КП и процессов (10 шагов).
- Чтение справочных данных из девяти систем-источников через витрину PostgreSQL.
- Генерация структурированных артефактов по шагам и их версионирование.
- Свободный чат и чат с методологом.
- Распознавание изображений и PDF (OCR через Vision API).
- Хранение истории всех диалогов и проектов.

### Вне границ [код] / [вывод]

- **Запись в системы-источники.** Продукт только читает данные; никакие
  изменения в СберБуст, Гемба, ARIS и прочие системы не вносятся.
- **Принятие управленческих решений.** Результат — рекомендация человеку;
  инициативы утверждает спонсор редизайна.
- **Автоматическое исполнение инициатив.** Продукт формирует карточки
  инициатив, но не запускает их реализацию.
- **Загрузка данных в витрину.** Наполнение схемы `reference_data` выполняется
  внешними процессами (`app/scripts/load_reference_data.py`), не пользователем.

## 5. Функциональные требования

### 5.1. Методология редизайна — ядро продукта

**FR-1. Продукт ведёт пользователя по методологии из десяти шагов, сгруппированных в три этапа [код] [ТЗ]**

| Этап | Шаг | Название | Артефакт |
|---|---|---|---|
| Подготовка | 0 | Выбор КП и процессов | Сводный отчёт по данным систем-источников |
| **Kick-off** | 1 | Контекст | Объект редизайна, характеристики, проблемы, мотивация |
| | 2 | Problem Statement и критерии успеха | PS + критерии по КГБ (качество, график, бюджет) |
| | 3 | Границы редизайна | Продукт / КП / Процесс + ограничения |
| | 4 | Дерево гипотез решений | Рычаги решений и гипотезы (≤5 на рычаг) |
| **Диагностика** | 5 | План исследований | План проверки гипотез |
| | 6 | Синтез диагностики | Обобщение результатов |
| | 7 | Дерево решений | Варианты решений |
| **Дизайн** | 8 | Карточки инициатив | Перечень инициатив |
| | 9 | Executive Summary | One-page для спонсора |

Привязка шагов к этапам взята из системных промптов
(`app/services/step_configs/system_messages/step_N.md`, строка «Этап:») и из
docstring артефактов (`step2.py`, `step3.py`, `step4.py`). Реализация шагов —
`app/services/step_configs/step0.py` … `step9.py`, маршрутизация в
`app/ui/redesign_steps.py`.

**FR-2. Артефакт каждого шага имеет строго заданную структуру [код]**

Формат артефакта описан Pydantic-моделью и валидируется при генерации.
Например, шаг 4 требует иерархию «рычаг решения → гипотеза → обоснование» с
ограничением не более пяти гипотез на рычаг (`step4.py`, `SolutionLever`).
Ответ языковой модели, не соответствующий схеме, артефактом не становится.

**FR-3. Артефакты шагов обязаны быть согласованы между собой [ТЗ]**

ТЗ v1 задаёт два вида критериев, которых в реализации сейчас нет как проверок:

- **консистентность внутри шага** — элементы одного артефакта не противоречат
  друг другу;
- **консистентность между шагами** — например, Executive Summary (шаг 9)
  обязан опираться на выводы шагов 1, 2, 6, 7 и 8; элементы шага 2 должны
  соотноситься со всеми элементами шага 1.

**[пробел]** Сейчас согласованность обеспечивается только тем, что предыдущие
артефакты подаются в контекст (`db.get_previous_artifacts`). Автоматической
проверки противоречий нет — требование остаётся на человеке.

**FR-4. Пользователь управляет версиями артефакта [код]**

Каждый шаг хранит несколько версий артефакта; активная версия выбирается
пользователем (`set_step_active_version`, `get_artifact_by_version` в
`app/core/database.py`). Сообщения диалога привязаны к версии, поэтому
переключение версии восстанавливает и соответствующий ход обсуждения.

**FR-5. На шаге 4 доступен поиск во внешних источниках [код]**

Признак `WEB_SEARCH_ENABLED = True` установлен только для шага «Дерево гипотез
решений» — это единственный шаг, где агенту разрешено выходить за пределы
внутренних данных.

### 5.2. Работа с данными систем-источников

**FR-6. Продукт автоматически собирает данные по коду процесса из девяти систем [код]**

| Система | Что содержит | Оговорка из промпта |
|---|---|---|
| `sberboost` | Предложения сотрудников по улучшениям | — |
| `pro_mnenie` | Опрос удовлетворённости внутренними сервисами (CSI) | — |
| `gemba` | Наблюдения руководства и утверждённые мероприятия | Обязательны к выполнению, но **не всегда реализуются** |
| `gt_suggestions` | Предложения территориальных подразделений | — |
| `gt_benchmark` | Наблюдения за внешним рынком, сравнение с конкурентами | — |
| `sberbpm` | Статистика процессов по цифровым следам | Шаги процесса могут **отличаться от реальных** |
| `aris` | Официальные бизнес-описания КП и процессов | Реальность **отличается**: процессы меняются быстрее документации |
| `stats` | Статистика по процессам | — |
| `kp_process` | Связь клиентских путей и процессов | — |

Реализация: `app/services/data_retrieval.py`, схема `reference_data`.

**FR-7. Продукт обязан явно сообщать об отсутствии данных [код]**

Требование зафиксировано в системном промпте шага 0: «Если данных из какой-то
системы нет — явно укажи это в отчёте». Молчаливый пропуск источника
недопустим: пользователь должен понимать, на какой доказательной базе построен
вывод.

**FR-8. Отчёт шага 0 строится только на фактах [код]**

Промпт задаёт принципы: фактологичность (без оценочных суждений и гипотез),
полнота, структурированность, беспристрастность. Интерпретации появляются
только начиная с шага 1.

### 5.3. Дополнительные режимы

**FR-9. Чат с методологом [код]** — отдельный режим для вопросов по самой
методологии редизайна, вне контекста конкретного проекта (`app/ui/methodology_logic.py`).

**FR-10. Свободный режим [код]** — чат с моделью без методологических
ограничений (`app/ui/free_mode_logic.py`).

**FR-11. Распознавание документов [код]** — загрузка изображений и PDF,
извлечение текста через Vision API GigaChat (`app/services/vision_service.py`).
Обработка асинхронная, через очередь фоновых задач (`app/services/task_worker.py`,
таблица `background_tasks`); пользователь не блокируется на время распознавания.

**FR-12. Извлечение текста из офисных файлов [код]** — поддерживаются PDF,
DOCX, PPTX, XLSX (`app/services/utils.py`, зависимости `pypdf`, `python-docx`,
`python-pptx`, `openpyxl`, `PyMuPDF`).

### 5.4. Доступ и учёт работы

**FR-13. Вход по логину и паролю [код]** — `app/core/auth.py`.

**FR-14. История работы сохраняется [код]** — чаты методолога, свободные чаты,
проекты редизайна, сообщения шагов, история распознавания (схема `app`).
Предусмотрена выгрузка истории пользователя (`app/scripts/export_user_history.py`).

**FR-15. Разграничение доступа между пользователями [пробел]**

Текущая реализация не соответствует требованию: при вводе несуществующего
логина пользователь **создаётся автоматически** (`auth.py`, ветка
«Auto-register for demo»), пароль хешируется одним проходом SHA-256 без соли.
В самом коде это помечено как демо-режим: «production should use bcrypt/argon2».
Для промышленного использования требуется интеграция с корпоративной
аутентификацией и ролевая модель.

## 7. Данные и интеграции

**Хранилище:** PostgreSQL 17, две схемы **[код]**

- `reference_data` — справочные данные систем-источников (относительно статичные);
- `app` — оперативные данные: пользователи, чаты, редизайны, шаги, артефакты,
  сообщения, история распознавания, очередь фоновых задач.

Разделение схем существенно с точки зрения бизнеса: справочные данные
загружаются извне и пользователем не меняются, а результаты работы пользователя
изолированы от источников.

**Внешние сервисы [код]:** OpenAI API, GigaChat (в т. ч. Vision), Anthropic API,
Phoenix (наблюдаемость).

## 8. Ограничения и допущения

1. **Данные источников неточны по своей природе [код].** Промпт прямо
   предупреждает о расхождениях ARIS и SberBPM с реальностью и о том, что
   утверждённые на Гемба мероприятия не всегда выполняются. Продукт обязан
   передавать эту неопределённость пользователю, а не сглаживать её.
2. **Результат — рекомендация, а не решение [вывод].** Ответственность за
   инициативы остаётся на аналитике и спонсоре редизайна.
3. **Качество зависит от полноты витрины [вывод].** Если процесс не покрыт
   системами-источниками, шаг 0 даст скудный отчёт, и вся последующая цепочка
   будет опираться на ввод пользователя.
4. **Текущий статус — PoC [код].** Версия 0.0.2, демонстрационная
   аутентификация, каталог `app/archive/` с прошлыми реализациями, дубли файлов
   (`step1 copy.py`, `stepbystep copy.ipynb`) — признаки исследовательской стадии.

## 9. Риски

| Риск | Последствие | Смягчение |
|---|---|---|
| Автоматическая регистрация пользователей | Доступ к внутренним данным о процессах банка получает любой, кто открыл приложение | Интеграция с корпоративной аутентификацией до вывода за пределы пилота |

| Зависимость от внешних LLM-провайдеров | Недоступность API останавливает работу | Реестр провайдеров уже есть; нужен регламент переключения |
