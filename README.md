# PKO

Восстанавливает паспорта объектов управления, таксономию, сравнение версий и
BASIC Gate Card по коду репозитория — по стандарту автономного процесса v1.1
([autonomous_process_standard_v1_1.md](autonomous_process_standard_v1_1.md)).

Зависимостей нет: только стандартная библиотека Python 3.11+ и `git`.

## Запуск

```bash
# клон от вашего имени по SSH + анализ двух версий
PYTHONPATH=src python3 -m pko.cli analyze \
  ssh://git@<bitbucket-host>:7999/<project>/<repo>.git

# уже существующий локальный клон, без сети
PYTHONPATH=src python3 -m pko.cli analyze --repo-path ~/src/<repo>

# какие версии будут обсчитаны
PYTHONPATH=src python3 -m pko.cli history --repo-path tests/fixtures/mini_repo --max-versions 6

# только карточка допуска, с готовым отчётом тестов
PYTHONPATH=src python3 -m pko.cli gate --repo-path . --junit reports/junit.xml
```

Полезные флаги: `--max-versions` (сколько точек истории), `--branch`,
`--no-fetch` (не обновлять зеркало), `--junit`, `--intent`, `--llm`,
`--publish` (заменить отчёты; по умолчанию в текущем каталоге, со снятием `.bak`).
Публикация откажется писать в каталог, где нет ни одного из заменяемых файлов, —
чтобы случайный `--publish-dir` не превратился в запись в чужое место.

`--junit` прикладывается только к последней версии: отчёт о тестах доказывает
поведение того кода, на котором его получили. Для остальных версий в отчёт
попадает пометка, что доказательства тестами не применялись. `--intent`
применяется ко всем версиям (иначе исторические стали бы черновиками), но для
неголовных версий в пробелы пишется, что подтверждение владельца относится к
другой версии.

Отчёты пишутся в `pko-out/` (каталог рабочий, в репозиторий не коммитится):
`taxonomy*.html`, `passports*.html`, `gate_card*.md`, `diff_*.md`,
`comparison_*.html` и машинная модель `pko_*.json`.

Коды возврата — для CI:

| Код | Значение |
|---|---|
| `0` | допуск выдан (`ALLOW` или `ALLOW_WITH_RESTRICTIONS`) |
| `3` | отказ в допуске (`DENY`) либо требуется полный контур |
| `4` | решение **не выносилось**: `business_intent.yaml` отсутствует или не заполнен |
| `1` | ошибка запуска: нет доступа, не разобрана ссылка, нет репозитория |
| `2` | некорректные аргументы CLI, например `--max-versions 0` |

Код `4` намеренно отделён от `3`: незаполненный ручной вход — это не отказ.

## Как устроено

```
SSH-ссылка → зеркало (--mirror, без рабочего дерева)
           → факты со ссылкой path:line@commit
           → кандидаты (роуты, узлы графа, инструменты, модули, лимиты)
           → PKO-модель
           → детерминированная валидация
           → BASIC Gate
           → отчёты
```

Три правила, на которых всё держится:

1. **Клон только на чтение.** Мутирующие команды git разрешены единственному
   модулю `pko/git/remote.py` (`clone --mirror`, `fetch`). В `pko/git/repo.py`
   стоит allowlist подкоманд — `checkout`, `reset`, `push` упадут до запуска git.
   Ключи не читаются и не хранятся: аутентификация целиком у вашего ssh-agent.
2. **Утверждение без ссылки не существует.** У каждого поля паспорта есть
   происхождение (`OBSERVED`, `DECLARED`, `INFERRED`, `UNKNOWN`, …) и ссылки на
   факты. В отчёт идут только путь, строка и краткое основание — текст кода не
   сохраняется и не публикуется, значения параметров с именами вида `*_key`,
   `*_token`, `*_secret` маскируются при извлечении.
3. **Языковая модель не выдаёт допуск.** Решение Gate считает
   `pko/gate/decide.py` по псевдокоду §5.2.3.4. `PASS` без доказательства
   нормализуется в отсутствующий результат, а он для обязательной проверки
   означает `FAIL` (§5.2.3.2).

## Языковые модели: две роли

Обе опциональны — без них PKO работает целиком и выдаёт те же статусы.

| Роль | Модель | Что делает | Что видит |
|---|---|---|---|
| `assembler` | GLM-5.2 | группирует кандидатов в BBB, возвращает только JSON | список кандидатов: id, тип, имя, пакет, путь |
| `writer` | DeepSeek-V4-Flash | пишет русский текст обзора и оценки изменений | готовую модель в JSON |

Сборщик обязан ссылаться на существующие `candidate_id` — всё остальное
отбрасывается. Текст писателя проверяет `pko/report/guard.py`: если в нём
появился идентификатор или путь, которых нет в модели, текст **целиком**
отбрасывается и отчёт собирается детерминированным шаблоном. Ошибку сборщика
ловит не вторая модель, а `pko/checks/validator.py`; смысловую корректность
сборки проверяет человек — для этого в паспорт каждого BBB выписан список
кандидатов, из которых он собран.

Endpoint'ы берутся из окружения (ключи только оттуда, в отчёты и кеш не попадают):

```bash
export PKO_ASSEMBLER_BASE_URL=...   # запасные имена: GLM_52_API, GLM_51_API
export PKO_ASSEMBLER_MODEL=GLM-5.2
export PKO_ASSEMBLER_API_KEY=...
export PKO_WRITER_BASE_URL=...      # запасные имена: DEEPSEEK_FLASH_API_BASE
export PKO_WRITER_MODEL=DeepSeek-V4-Flash
export PKO_WRITER_API_KEY=...
```

Ответы кешируются в `~/.pko/llm-cache` по (endpoint, промпт), температура 0 —
повторный прогон того же коммита даёт тот же отчёт.

## Ручной вход

Потребность, целевое состояние, границы автономности и владельца результата из
кода вывести нельзя (§4.0). Их подтверждает человек в `business_intent.yaml`
рядом с кодом — образец в [examples/business_intent.yaml](examples/business_intent.yaml).
Файла нет — или он есть, но обязательные поля (`confirmed_need_id`,
`business_owner`, `target_state`, `success_criteria`) не заполнены — PKO выпускает
черновик: модель и отчёты строятся, но решение Gate **не выносится**, карточка
получает статус `NO_DECISION`, а команда — код возврата `4`. Это отдельный сигнал,
а не отказ в допуске: `NO_DECISION` ничего не разрешает, верхняя граница режима
остаётся пустой.

Поля профилирования — закрытые перечни (`maturity`, `consequence`,
`requested_mode`, `scale`, `decision_boundary`). Неизвестное непустое значение —
не повод подставить мягкий вариант по умолчанию: такой файл к решению не
допускается, и карточка называет конкретное поле. `consequence: hgh` даст
`NO_DECISION`, а не BASIC-пилот. Дополнительно само профилирование ошибается в
строгую сторону: нераспознанная зрелость считается промышленным запуском,
нераспознанная значимость — высокой, нераспознанный режим — триггером FULL.

## Связь «тест ↔ ограничение»

Тесты анализируемого проекта PKO не запускает, поэтому единственное доказательство
для guardrail — готовый JUnit XML. Связь строится по именам тестов
(`src/pko/checks/test_link.py`) и намеренно строгая: для числового ограничения имя
теста должно содержать **все** значащие части ключа (`sql_timeout` → и `sql`, и
`timeout`) плюс маркер применения; для инварианта «только чтение» — и глагол
изменения данных, и маркер запрета. Имя подтвердившего теста выписывается в
паспорт, чтобы связь можно было проверить.

Доказательством считается только **пройденный** тест. Пропущенный не подтверждает
ничего: в реальных проектах часть сценариев штатно скипается guard'ом (например,
требующие живого LLM), и отчёт, где пропущено всё, формально не содержит падений.
Поэтому исход каждого теста хранится отдельно, `CHK-TEST-001` не проходит, если не
выполнился ни один тест, а негативные сценарии и guardrails сопоставляются только с
пройденными случаями.

Этот же модуль спрашивают и паспорт guardrail, и проверка Gate `CHK-GRD-001` —
поэтому карточка допуска и модель не могут разойтись в выводе об одном и том же
ограничении. Ограничение стоит понимать как приближение: совпадение имён не
доказывает, что тест действительно проверяет именно эту политику.

## Проверка

Одна команда, она же предназначена для сборочного контура:

```bash
make test          # == PYTHONPATH=src python3 -m unittest discover -s tests
```

Тестовый репозиторий создаётся автоматически при первом обращении
(`tests/fixture_support.ensure_fixture`), отдельный шаг не нужен: сам репозиторий
в версионном контроле не хранится, поэтому на чистом клоне набор раньше молча
пропускался. Скрипт `tests/make_fixture.sh` пишет файлы через `cat` и не
использует непереносимых ключей; проверен на macOS (bash 3.2, git 2.39+) и на
Linux с GNU coreutils. Если репозиторий собирается pytest'ом, конфигурация лежит
в `[tool.pytest.ini_options]` в `pyproject.toml`.

Пример полного прогона на фикстуре:

```bash
PYTHONPATH=src python3 -m pko.cli analyze --repo-path tests/fixtures/mini_repo --out pko-out
```

В наборе — 95 тестов: три нормативных сценария профилирования §Б.4 с обратной
проверкой, приоритеты решений §5.2.3.3, воспроизведение вердикта примера §Б.1.3,
детерминизм модели, согласованность паспорта guardrail с вердиктом Gate, отчёт с
полностью пропущенными тестами, опечатки в перечнях профилирования, контракт кодов
возврата, устойчивость сравнения версий к перенумерации `BBB/AO/GRD-NNN`, выбор
базовой версии по анализируемой ветке, разбор SQL в комментариях, защиту публикации
и падение сборки отчёта при выдуманном идентификаторе в тексте.

Если фикстуру не удалось собрать, прогон падает, а не пропускает тесты: молчаливый
пропуск 27 сквозных проверок при зелёном итоге — та самая потеря сигнала, которую
самобутстрап и должен был закрыть.

## Границы первой версии

- Разбирается Python (FastAPI, LangGraph), `pyproject.toml`, `requirements*.txt`,
  `package.json`, YAML/TOML/INI, `.env*`, CODEOWNERS, JUnit XML. **Фронтенд на
  TypeScript не анализируется** — доля разобранных файлов всегда показана в
  шапке отчёта, чтобы пустая модель не выглядела «чистой».
- Тесты анализируемого проекта не запускаются. Без готового `junit.xml` проверки
  «поведение доказано тестом» дают `FAIL` — это ожидаемое поведение, а не сбой.
- Динамические переходы графа статическому разбору не видны.
- Ограничение «только чтение» без негативного теста не может получить статус
  выше `OBSERVED`: регулярное выражение не видит динамический SQL.
