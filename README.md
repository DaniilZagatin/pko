# PKO

Восстанавливает паспорта объектов управления, таксономию, сравнение версий и
BASIC Gate Card по коду репозитория — по стандарту автономного процесса v1.1
([autonomous_process_standard_v1_1.md](autonomous_process_standard_v1_1.md)).

Зависимостей нет: только стандартная библиотека Python 3.11+ и `git`.

## Запуск

Пошаговый сценарий для первого внутреннего репозитория: [FIRST_RUN.md](FIRST_RUN.md).

```bash
# клон от вашего имени по SSH + анализ двух версий
PYTHONPATH=src python3 -m pko.cli analyze \
  ssh://git@<bitbucket-host>:7999/<project>/<repo>.git

# уже существующий локальный клон, без сети
PYTHONPATH=src python3 -m pko.cli analyze --repo-path ~/src/<repo>

# какие версии будут обсчитаны
PYTHONPATH=src python3 -m pko.cli history --repo-path tests/fixtures/mini_repo --max-versions 6

# только запись допуска: gate_card.md и basic_gate.json, с готовым отчётом тестов
PYTHONPATH=src python3 -m pko.cli gate --repo-path . --junit reports/junit.xml
```

Полезные флаги: `--max-versions` (сколько точек истории), `--branch`,
`--no-fetch` (не обновлять зеркало), `--junit`, `--intent`, `--llm`,
`--publish` (заменить отчёты; по умолчанию в текущем каталоге, со снятием `.bak`).
Публикация откажется писать в каталог, где нет ни одного из заменяемых файлов, —
чтобы случайный `--publish-dir` не превратился в запись в чужое место.

`--junit` и `--intent` прикладываются только к последней версии, и по одной
причине: доказательство относится к тому коду, на котором его получили. Отчёт о
тестах прогоняли на конкретном коммите, намерение владелец подтверждал для
конкретного коммита. Для остальных версий намерение берётся из самого коммита —
нет его там, решение о допуске для этой версии не выносится, и в пробелах прямо
сказано, что флаг к ней не применялся. Историческая версия становится
черновиком, и это правильный исход: выдавать допуск версии по чужому
подтверждению нельзя.

Отчёты пишутся в `pko-out/` (каталог рабочий, в репозиторий не коммитится).
Читать начинают с одного файла:

| Файл | Что отвечает |
|---|---|
| `index.html` | **точка входа.** Можно ли запускать, что мешает, как устроена система, чего анализ не покрыл |
| `passports*.html` | паспорта объектов: картотека и подробности по клику |
| `taxonomy*.html` | полный состав объектов управления |
| `gate_card*.md` | карточка допуска §5.1.1 в читаемом виде |
| `comparison_*.html`, `diff_*.md` | что изменилось между версиями |
| `basic_gate.json` | запись допуска `BASIC_RECORD` §8.0.1: scope, снимок реализации, проверки, решение, срок действия |
| `full_readiness.json` | готовность к промышленному контуру §6 по областям — отдельно от допуска |
| `standard_coverage.json` | какие требования стандарта PKO проверяет, а какие нет |
| `semantic_facts.json` | все наблюдения с фасетами и доказательствами |
| `pko_*.json` | машинная модель версии |

`index.html` открывается с диска и не тянет ни одного внешнего ресурса: в
закрытом контуре отчёт с CDN-ссылками — пустая страница.

Записи `basic_gate.json` и `full_readiness.json` разведены намеренно. Профиль
`FULL` означает, что промышленные требования §6 **применяются**, а не что они
выполнены: PKO выпускает машинный уровень `BASIC_RECORD` и при профиле `FULL`
честно печатает «требуется `FULL_RESOURCE_MODEL`, выпущено `BASIC_RECORD`».
Что именно проверяется, а что нет, перечислено в
[`docs/standard_coverage.md`](docs/standard_coverage.md) — файл собирается из
машинного каталога требований командой `make coverage-doc`.

Коды возврата — для CI:

| Код | Значение |
|---|---|
| `0` | допуск выдан (`ALLOW` или `ALLOW_WITH_RESTRICTIONS`) |
| `3` | отказ в допуске (`DENY`) либо требуется полный контур |
| `4` | решение **не выносилось**: `business_intent.yaml` отсутствует или не заполнен |
| `1` | ошибка запуска: нет доступа, не разобрана ссылка, нет репозитория |
| `2` | некорректные аргументы CLI, например `--max-versions 0` |

Код `4` намеренно отделён от `3`: незаполненный ручной вход — это не отказ.

## Как устроено

```
SSH-ссылка → зеркало (--mirror, без рабочего дерева)
           → факты со ссылкой path:line@commit
           → кандидаты (роуты, узлы графа, инструменты, модули, лимиты)
           → PKO-модель
           → детерминированная валидация
           → BASIC Gate
           → отчёты
```

Три правила, на которых всё держится:

1. **Клон только на чтение.** Мутирующие команды git разрешены единственному
   модулю `pko/git/remote.py` (`clone --mirror`, `fetch`). В `pko/git/repo.py`
   стоит allowlist подкоманд — `checkout`, `reset`, `push` упадут до запуска git.
   Ключи не читаются и не хранятся: аутентификация целиком у вашего ssh-agent.
2. **Утверждение без ссылки не существует.** У каждого поля паспорта есть
   происхождение (`OBSERVED`, `DECLARED`, `INFERRED`, `UNKNOWN`, …) и ссылки на
   факты. В отчёт идут только путь, строка и краткое основание — текст кода не
   сохраняется и не публикуется, значения параметров с именами вида `*_key`,
   `*_token`, `*_secret` маскируются при извлечении.
3. **Языковая модель не выдаёт допуск.** Решение Gate считает
   `pko/gate/decide.py` по псевдокоду §5.2.3.4. `PASS` без доказательства
   нормализуется в отсутствующий результат, а он для обязательной проверки
   означает `FAIL` (§5.2.3.2).

## Языковые модели: три роли

Все опциональны — без них PKO работает целиком и выдаёт те же статусы.

| Роль | Модель | Что делает | Что видит |
|---|---|---|---|
| `scout` | задаётся флагом | агент разведки: читает репозиторий сам и предлагает объекты | **файлы репозитория** |
| `assembler` | GLM-5.2 | группирует кандидатов в BBB, возвращает только JSON | список кандидатов: id, тип, имя, пакет, путь |
| `writer` | DeepSeek-V4-Flash | пишет русский текст обзора и оценки изменений | готовую модель в JSON |

Сборщик обязан ссылаться на существующие `candidate_id` — всё остальное
отбрасывается. Текст писателя проверяет `pko/report/guard.py`: если в нём
появился идентификатор или путь, которых нет в модели, текст **целиком**
отбрасывается и отчёт собирается детерминированным шаблоном. Ошибку сборщика
ловит не вторая модель, а `pko/checks/validator.py`; смысловую корректность
сборки проверяет человек — для этого в паспорт каждого BBB выписан список
кандидатов, из которых он собран.

Endpoint'ы берутся из окружения (ключи только оттуда, в отчёты и кеш не попадают):

```bash
export PKO_ASSEMBLER_BASE_URL=...   # запасные имена: GLM_52_API, GLM_51_API
export PKO_ASSEMBLER_MODEL=GLM-5.2
export PKO_ASSEMBLER_API_KEY=...
export PKO_WRITER_BASE_URL=...      # запасные имена: DEEPSEEK_FLASH_API_BASE
export PKO_WRITER_MODEL=DeepSeek-V4-Flash
export PKO_WRITER_API_KEY=...
```

Ответы кешируются в `~/.pko/llm-cache` по (endpoint, промпт), температура 0 —
повторный прогон того же коммита даёт тот же отчёт.

## Агент разведки (`--agent`)

Детерминированные экстракторы знают ограниченный набор фреймворков: на проекте,
чей стек им незнаком, траектория не восстановится, а BBB выродятся в имена
каталогов. Агент читает репозиторий сам и потому не привязан к списку
поддержанных фреймворков.

Наблюдение описывается тремя независимыми признаками, а не одним видом:

| Признак | Что отвечает | Примеры |
| --- | --- | --- |
| `category` | чем это является в процессе | `ENTRYPOINT`, `STEP`, `EFFECT`, `CONTROL`, `COMPONENT`, `STATE`, `UNKNOWN`, `CONTRADICTION` |
| `action` | что оно делает | `read`, `write`, `call`, `serve`, `emit`, `transition` |
| `mechanism` | чем именно сделано | `sql`, `orm`, `http_server`, `ui_event`, `cli`, `cron`, `queue`, `fs`, `llm`, `graph` |

SQL перестал быть отдельной сущностью: запись в базу — это `EFFECT/write/sql`,
клик в интерфейсе — `ENTRYPOINT/serve/ui_event`, отправка в очередь —
`EFFECT/emit/queue`. Новая технология требует одного значения `mechanism`, а не
правки модели. Прежние виды (`SQL_READ`, `ROUTE`, `GRAPH_NODE` и остальные)
сохранены как псевдонимы с точным разложением в `src/pko/model/taxonomy.py`,
поэтому старые отчёты и проверки продолжают работать.

```bash
export PKO_SCOUT_ALLOWED_HOSTS='<internal-llm-host>'
PYTHONPATH=src python3 -m pko.cli analyze --repo-path . --agent \
  --scout-base-url https://<endpoint>/v1 --scout-model GLM-5.2 \
  --scout-api-key-env PKO_SCOUT_API_KEY
```

Что важно понимать до включения:

- **Код уходит только на явно разрешённый host.** `writer` видит только модель,
  а `scout` читает файлы. Перед запуском нужно задать точные внутренние hosts в
  `PKO_SCOUT_ALLOWED_HOSTS` или `--scout-allowed-hosts`; без allowlist запуск
  закрыт, а endpoint на другом host отклоняется до первого запроса.
- **Ключ передаётся именем переменной окружения**, а не значением: значение во
  флаге осело бы в истории оболочки и в выводе `ps`.
- **Инструменты только на чтение** и привязаны к коммиту: `list_files`,
  `read_file`, `search`, `note_fact`. Bash нет намеренно — allowlist подкоманд в
  `pko/git/repo.py` тем и ценен, что доказывает «анализ ничего не меняет».
  Vendor-каталоги скрыты, файлы `.env*` не выдаются, значения параметров с
  именами вида `*_key`/`*_token` маскируются.
- **Каждый факт перепроверяется кодом** (`pko/agent/verify.py`): путь и строка
  должны существовать на том же коммите, а в окрестности строки должен найтись
  якорь из формулировки. Не подтвердилось — факт отбрасывается, причина уходит в
  трассу. `OBSERVED` по-прежнему означает «код это показывает».
- **Механизм обязателен для наблюдения.** Без него структурной проверки не
  существует: подтверждать нечего, и наблюдение попадало бы в паспорт с
  происхождением `OBSERVED`, имея за собой лишь совпадение слова из
  формулировки. Исключение — `UNKNOWN` и `CONTRADICTION`: у них механизма нет
  по смыслу, и ни одно поле паспорта их не показывает. Опечатка в `action`
  тоже отклоняется, а не стирается. Правило одно для обоих путей приёма —
  `taxonomy.proposal_problem`.
- **Признаки проверяются как целое.** Механизм подтверждается конструкцией, а
  допустимые для него категории заданы таблицей `MECHANISM_CATEGORIES`: запись
  в файл не может быть точкой входа, а прежний вид (`SQL_WRITE`) нельзя
  переобъявить другой категорией. Иначе ошибка классификации меняла бы вход
  детерминированного Gate при верной конструкции.
- **Механизм проверяется структурно** реестром `pko/agent/verifiers/`: рядом со
  ссылкой должна стоять сама конструкция — вызов, декоратор, ключевое слово, —
  и она обязана совпадать по направлению с действием: отправка в очередь не
  доказывает обработчик, ребро графа не доказывает узел, чтение не доказывает
  запись. Нет шаблона под сочетание — наблюдение остаётся в отчёте, но вердикта
  не касается.
  Строковые литералы и docstring маскируются до проверки. SQL является строкой
  по определению, поэтому SQL-находка scout остаётся в отчёте, но не становится
  Gate evidence: для Gate используется детерминированный Python-экстрактор.
- **Незнакомый механизм попадает в отчёт, но не в вердикт.** Подтвердить его
  структурно PKO пока не умеет, поэтому наблюдение видно в паспорте и в
  пробелах, а решение о допуске им подкрепить нельзя. Это же различие
  выписано отдельным столбцом в `semantic_facts.json`.
- **Вердикт Gate не меняется** — его считает тот же детерминированный код.
  Траектория и инварианты от агента получают `INFERRED`: это интерпретация.
  Перечень механизмов, на которые опираются проверки, задан в одном месте —
  `src/pko/gate/policies.py`, и там же сказано, какие из них расширяют смысл
  проверки. CHK-GRD-001 покрывает SQL и ORM — это прежний периметр; изменения
  данных в файлах, объектных хранилищах и документных базах в вердикт не
  входят и попадают в пробелы отчёта отдельной строкой. CHK-AP-001 теперь
  принимает точкой входа экранное событие, команду, расписание и очередь —
  это расширение, и на стеке без графа исполнения проверка может перейти из
  FAIL в PASS.
- **Промпт собирается под стек.** Ядро `prompts/scout_core.md` не называет ни
  одного фреймворка; примеры и признаки живут в паках `prompts/packs/*.md`
  (`web`, `data`, `agents`, `frontend`, `jobs`, `messaging`). Набор выбирается
  детерминированно по манифестам, расширениям и признакам механизмов
  (`src/pko/agent/stack.py`), пишется в трассу и переопределяется флагом
  `--agent-packs` для диагностики.
- **Первый проход независим от статических находок.** Начальное сообщение не
  содержит `facts_by_kind` и примеров SQL/FastAPI/LangGraph. После просмотра
  дерева агент вызывает `static_hints`; до первого `list_files`, `read_file`
  или `search` инструмент подсказок отказывает.
- **Периметр первой версии — backend.** Покрытие считается по Python и
  сопутствующей конфигурации; фронтенд (`.ts/.tsx/.css/.svg`) в знаменатель
  `CHK-COV-001` не входит и назван отдельной неблокирующей строкой. Иначе
  граница инструмента выглядела бы недостатком анализируемой системы: на
  реальной цели 42% «непокрытого» были файлами фронта. Пак `frontend` по той
  же причине не подключается сам — только явным `--agent-packs frontend`.
- **Текст модели в паспортах.** С `--llm` каждый объект получает пояснение в
  одно-два предложения: что это в работе системы и почему важно владельцу.
  Пояснение стоит до таблицы полей, а обзор системы — до паспортов. Сторож
  проверяет эти тексты так же строго, как обзор: выдуманный идентификатор
  или путь отбрасывает пояснение целиком.
- **Отчёт — витрина, а не выгрузка.** Таксономия показывает по одной короткой
  строке на объект, паспорта открываются картотекой карточек: подробности
  видны тогда, когда их спросили. Вид повторяет эталонные `taxonomy_v1_1.html`
  и `passports_v1_1.html`. Бейдж происхождения ставится только там, где
  значение не `OBSERVED`: «найдено в коде» — норма отчёта, и помечать норму
  значит помечать всё.
- **Доказательство читается словами.** В паспорте видно основание («эндпоинт
  POST /tasks»), а `путь:строка` идёт следом мелким шрифтом; хеш коммита из
  тела отчёта убран — он один на версию и стоит в шапке. В карточке допуска
  колонка «Ссылка на факт» тоже называет, что именно найдено по этой строке.
- **`--llm` не деградирует молча.** Пустой ответ писателя прерывает прогон
  (`LlmError`), пустой ответ не попадает в кеш, а запуск с `--llm` без
  настроенного endpoint останавливается до анализа. Раньше отчёт молча
  собирался шаблоном, и читатель принимал его за написанный моделью. Перечень расширений прикладного кода один на весь проект
  (`extractors/base.py`): по нему определяется стек, считается непокрытая
  часть и сторож `report/guard.py` проверяет пути в тексте писателя — иначе
  на чужом стеке одно из трёх молча перестало бы работать.
- **Шаги не ограничены** по умолчанию. Автоматический стоп один — три подряд
  идентичных вызова инструмента; он помечает прогон неполным. Ручной тормоз:
  `--agent-max-steps`.

### Трасса

Главный продукт режима — `agent_trace_<версия>.json` и `.html` рядом с отчётами:
полный ход разведки, включая содержимое прочитанных файлов, с пометками на
шагах, где факт был отброшен. По ней ищут, где агент ошибся, и правят промпт
(`src/pko/agent/prompts/scout_core.md` и паки; версия ядра, набор паков и хеш
собранного текста пишутся в трассу — прогоны с разными паками несравнимы).

Рядом с отчётами пишется `semantic_facts.json` — машинный срез всех наблюдений
всех разобранных версий: фасеты, доказательство, участие в вердикте и выбранные
паки. Он публикуется тем же транзакционным комплектом, что и отчёты, поэтому
данные и отчёт всегда относятся к одному прогону.

Трасса содержит код анализируемой системы — файл конфиденциален наравне с кешем
зеркал, права выставляются `0600`.

### Бенчмарк

```bash
export PKO_SCOUT_ALLOWED_HOSTS='<internal-llm-host>'
python3 bench/run_bench.py --scout-base-url ... --scout-model ... \
  --scout-api-key-env PKO_SCOUT_API_KEY
python3 bench/report.py            # сводная таблица по прогонам
```

Цели описаны в `bench/targets.yaml`, по умолчанию одна — самоанализ PKO. Одна
модель за прогон; сравнение моделей и редакций промпта делает `bench/report.py`
постфактум. Результаты складываются в `bench/runs/` (в репозиторий не попадают).

## Ручной вход

Потребность, целевое состояние, границы автономности и владельца результата из
кода вывести нельзя (§4.0). Их подтверждает человек в `business_intent.yaml`
рядом с кодом — образец в [examples/business_intent.yaml](examples/business_intent.yaml).
Файла нет — или он есть, но обязательные поля результата (`confirmed_need_id`,
`business_owner`, `target_state`, `success_criteria`) и границы полномочий
(`decision_boundary`, `in_scope`, `forbidden_effects`) не заполнены — PKO
выпускает черновик: модель и отчёты строятся, но решение Gate **не выносится**,
карточка получает статус `NO_DECISION`, а команда — код возврата `4`. Это
отдельный сигнал, а не отказ в допуске: `NO_DECISION` ничего не разрешает,
верхняя граница режима остаётся пустой. Если запрещённых эффектов действительно
нет, это подтверждается явно как `forbidden_effects: none`; пустое поле не
считается политикой. Отсутствующий `out_of_scope` также не расширяет `in_scope`.

Поля профилирования — закрытые перечни (`maturity`, `consequence`,
`requested_mode`, `scale`, `decision_boundary`). Неизвестное непустое значение —
не повод подставить мягкий вариант по умолчанию: такой файл к решению не
допускается, и карточка называет конкретное поле. `consequence: hgh` даст
`NO_DECISION`, а не BASIC-пилот. Дополнительно само профилирование ошибается в
строгую сторону: нераспознанная зрелость считается промышленным запуском,
нераспознанная значимость — высокой, нераспознанный режим — триггером FULL.

## Связь «тест ↔ ограничение»

Тесты анализируемого проекта PKO не запускает, поэтому единственное доказательство
для guardrail — готовый JUnit XML. Связь строится по именам тестов
(`src/pko/checks/test_link.py`) и намеренно строгая: для числового ограничения имя
теста должно содержать **все** значащие части ключа (`sql_timeout` → и `sql`, и
`timeout`) плюс маркер применения; для инварианта «только чтение» — и глагол
изменения данных, и маркер запрета. Имя подтвердившего теста выписывается в
паспорт, чтобы связь можно было проверить.

Доказательством считается только **пройденный** тест. Пропущенный не подтверждает
ничего: в реальных проектах часть сценариев штатно скипается guard'ом (например,
требующие живого LLM), и отчёт, где пропущено всё, формально не содержит падений.
Поэтому исход каждого теста хранится отдельно, `CHK-TEST-001` не проходит, если не
выполнился ни один тест, а негативные сценарии и guardrails сопоставляются только с
пройденными случаями.

Этот же модуль спрашивают и паспорт guardrail, и проверка Gate `CHK-GRD-001` —
поэтому карточка допуска и модель не могут разойтись в выводе об одном и том же
ограничении. Ограничение стоит понимать как приближение: совпадение имён не
доказывает, что тест действительно проверяет именно эту политику.

## Проверка

Две команды: одна печатает результат, вторая его записывает.

```bash
make test          # == PYTHONPATH=src python3 -m unittest discover -s tests
make test-report   # то же самое + reports/TESTS.txt и reports/junit.xml
```

Для сборочного контура, приёмки и любого внешнего гейта нужна вторая:
`make test` печатает результат в терминал, и он живёт до закрытия окна, а
`make test-report` оставляет запись — команду, код возврата, время и исход
каждого теста. Это то же требование, которое PKO предъявляет анализируемым
системам (§5.2.3.2: `PASS` без доказательства не является результатом), поэтому
и формат тот же: `reports/junit.xml` читается `pko analyze --junit`.

Обе команды не требуют ни сети, ни предварительно собранной фикстуры, ни
`PYTHONPATH`, и пишут только внутрь рабочего каталога — проверено на чистой
копии дерева. Каталог `reports/` не коммитится: записанный прогон относится к
конкретному состоянию кода, и в репозитории он однажды покажет зелёный отчёт для
кода, которого не касался.

Тестовый репозиторий создаётся автоматически при первом обращении
(`tests/fixture_support.ensure_fixture`), отдельный шаг не нужен: сам репозиторий
в версионном контроле не хранится, поэтому на чистом клоне набор раньше молча
пропускался. Скрипт `tests/make_fixture.sh` пишет файлы через `cat` и не
использует непереносимых ключей; проверен на macOS (bash 3.2, git 2.39+) и на
Linux с GNU coreutils. Если репозиторий собирается pytest'ом, конфигурация лежит
в `[tool.pytest.ini_options]` в `pyproject.toml`.

Пример полного прогона на фикстуре:

```bash
PYTHONPATH=src python3 -m pko.cli analyze --repo-path tests/fixtures/mini_repo --out pko-out
```

В наборе — более 400 тестов: три нормативных сценария профилирования §Б.4 с обратной
проверкой, приоритеты решений §5.2.3.3, воспроизведение вердикта примера §Б.1.3,
детерминизм модели, согласованность паспорта guardrail с вердиктом Gate, отчёт с
полностью пропущенными тестами, опечатки в перечнях профилирования, контракт кодов
возврата, устойчивость сравнения версий к перенумерации `BBB/AO/GRD-NNN`, выбор
базовой версии по анализируемой ветке, разбор SQL в комментариях, защиту публикации,
отсутствие технических ключей в разделе «Связи», падение сборки отчёта при
выдуманном идентификаторе в тексте, а также инструменты агента, отбраковку его
неподтверждённых фактов, стоп по повтору вызова и запись трассы.

Отдельно проверяется то, что PKO не должен утверждать: что запись допуска не
подставляет за владельца незаполненные поля §8.0.1, что при профиле `FULL`
машинный уровень не объявляется достигнутым, что объявленный в спецификации
маршрут и вынесенный в YAML лимит не дают допуска, что `index.html` открывается
без сети и согласован со всеми JSON-аудитами рядом, что подтверждение владельца
для сегодняшнего кода не выдаёт допуск исторической версии и что `pko gate`
выпускает ту же карточку, что и `pko analyze`.

Если фикстуру не удалось собрать, прогон падает, а не пропускает тесты: молчаливый
пропуск 27 сквозных проверок при зелёном итоге — та самая потеря сигнала, которую
самобутстрап и должен был закрыть.

## Границы первой версии

- Разбирается Python (FastAPI, LangGraph), `pyproject.toml`, `requirements*.txt`,
  `package.json`, YAML/TOML/INI, `.env*`, CODEOWNERS, JUnit XML, а также
  объявленные контракты: OpenAPI, JSON Schema, манифесты инструментов, политики
  и лимиты в конфигурации. **Фронтенд на TypeScript не анализируется** — доля
  разобранных файлов всегда показана в шапке отчёта, чтобы пустая модель не
  выглядела «чистой».
- Объявление — не реализация. Маршрут из OpenAPI и таймаут из YAML попадают в
  паспорта и в машинный срез, но допуск на них не выдаётся: иначе репозиторий с
  одной спецификацией и без кода проходил бы проверку «траектория
  восстанавливается из реализации».
- Тесты анализируемого проекта не запускаются. Без готового `junit.xml` проверки
  «поведение доказано тестом» дают `FAIL` — это ожидаемое поведение, а не сбой.
- Динамические переходы графа статическому разбору не видны.
- Контроля исполнения нет. PKO отвечает на вопрос «можно ли запускать», а не
  «соблюдается ли ограничение при каждом действии»: журнала запусков §8.0.2 он
  не производит, и в каталоге требований такие пункты помечены `NEEDS_RUNTIME` —
  это граница подхода, а не невыполненная работа. Что для этого нужно, описано в
  [`docs/runtime_poc.md`](docs/runtime_poc.md).
- Ограничение «только чтение» без негативного теста не может получить статус
  выше `OBSERVED`: регулярное выражение не видит динамический SQL.
