# PKO progress

Сравнивает PPTX-план команды (карточки задач, таймлайн-схема по этапам) с
кодом целевого репозитория и выпускает отчёт о прогрессе: что сделано, что
частично, что не начато, что сделано сверх плана.

## Структура репозитория

```
backend/pko/    — весь Python-код: пайплайн, CLI, веб API (FastAPI, JSON+SSE)
frontend-web/   — веб-интерфейс: загрузка → живой прогресс → dashboard (Next.js)
frontend-app/   — React-компонент секции «Путь» встроенного HTML-отчёта (см. ниже), Node-проект
tests/
```

`backend`/`frontend-web` — раздельные каталоги верхнего уровня, а не фронтенд
внутри пакета: `pip install` пакета `frontend-web/` не затрагивает.
`backend/pko/web/app.py` отдаёт только JSON/SSE под `/api/*` — HTML он не
рендерит и не раздаёт, это отдельный процесс `frontend-web/` (`npm run dev`
локально, `next build && next start` в проде), который ходит на этот API. Для
офлайн-отчёта без веб-сервера (`pko progress` → один файл `progress_report.html`)
UI не нужен вовсе — это независимый путь через `render/progress_report.py`.

## Установка

```bash
pip install -e .
```

Дашборд-путь в отчёте (шевроны с заливкой по % готовности) рисует собранный
React-компонент — соберите его один раз (нужен Node.js/npm; собранный файл
не коммитится в git):

```bash
cd frontend-app
npm install
npm run build     # -> frontend-app/dist/index.html
```

Без этого шага `pko progress`/`pko serve` упадут понятной ошибкой
(«Дашборд-путь не собран») в момент рендера отчёта, если в плане вообще есть
пункты — само чтение плана и работа агента от сборки фронтенда не зависят.

Веб-интерфейс (`frontend-web/`) — отдельный Next.js-проект, тоже разовая
установка (нужен тот же Node.js/npm, ставится независимо от `frontend-app/`):

```bash
cd frontend-web
npm install
```

## Запуск

Веб-интерфейс — два процесса одновременно, в разных терминалах: бэкенд отдаёт
только JSON/SSE, страницы рисует `frontend-web`.

```bash
# терминал 1 — бэкенд: JSON+SSE API на http://127.0.0.1:8000, без своего UI
python3 -m pko.cli serve

# терминал 2 — сам интерфейс: http://localhost:3000 (загрузка → прогресс → dashboard)
cd frontend-web && npm run dev
```

`frontend-web` в dev-режиме проксирует `/api/*` на бэкенд через `rewrites()`
в `next.config.ts` (по умолчанию `http://127.0.0.1:8000` — переопределяется
переменной `PKO_BACKEND_URL`, если `pko serve` поднят на другом порту/хосте).
В проде вместо `npm run dev` — `npm run build && npm run start`, оба процесса
должны стоять за одним обратным прокси (иначе браузер увидит два разных
origin и упрётся в CORS — сейчас на бэкенде она не настроена).

Офлайн-отчёт (`pko progress` — один файл `progress_report.html`, без сервера
и без `frontend-web`) — как и раньше, через CLI:

```bash
# CLI, план + уже существующий локальный клон целевого репозитория
python3 -m pko.cli progress plan.pptx --repo-path ~/src/<repo>

# CLI, план + репозиторий по SSH-ссылке (клонируется зеркалом, read-only)
python3 -m pko.cli progress plan.pptx \
  ssh://git@<host>:7999/<project>/<repo>.git
```

Без `pip install -e .` (или вместо неё) — `PYTHONPATH=backend python3 -m pko.cli ...`.

`pko serve` — локальный инструмент: сервер слушает `127.0.0.1` по умолчанию,
не `0.0.0.0` — не рассчитан на доступ с других машин. `POST /api/analyses`
принимает репозиторий и файлы проекта как два независимых необязательных
поля (не выбор одного из вариантов) — можно оба сразу (объединяются в один
анализ, `progress/local_source.py`), можно только один, можно ни одного:
пустой снимок материалов — не ошибка запроса, агент сам решает, что писать
в вердикт, когда подтвердить пункт плана нечем (подробнее — «Как устроено»
ниже). Поле «репозиторий» принимает и SSH-ссылку, и локальный путь
(автоопределение) — SSH-ключ отдельно никуда не передаётся, доступ идёт через
уже настроенный на машине с `pko serve` SSH-agent.

Полезные флаги `progress`: `--branch`, `--out` (каталог отчёта, по умолчанию
`pko-progress-out/`), `--no-fetch` (не обновлять зеркало). У `serve`:
`--host`, `--port`.

## LLM-доступ

Две роли, обе — на любом OpenAI-совместимом эндпоинте (`/chat/completions`):

| Роль | Что делает | Обязательна? |
|---|---|---|
| `matcher` | единый агент: за одну сессию сам выделяет пункты плана из текста слайдов и, по одному пункту за раз, ищет по коду репозитория подтверждение | да — без неё нет отчёта |
| `reporter` | вердикты по всем пунктам сразу → связный текстовый вывод | нет — без неё просто не будет раздела «Итог» |

По умолчанию обе используют одни и те же переменные:

```bash
export PKO_ASSEMBLER_BASE_URL=...   # например, внутренний GLM-совместимый endpoint
export PKO_ASSEMBLER_MODEL=GLM-5.2
export PKO_ASSEMBLER_API_KEY=...
```

Если какой-то роли нужна другая модель — `PKO_MATCHER_*`/`PKO_REPORTER_*`
переопределяют общий дефолт по отдельности. Без `matcher` и CLI, и веб
останавливаются до анализа с понятной причиной, а не собирают пустой отчёт;
после смены переменных `pko serve` нужно перезапустить, чтобы он их подхватил.

Ответы кешируются в `~/.pko/llm-cache` по (endpoint, промпт), температура 0.

## Как устроено

```
PPTX-план
  → чтение слайдов (текст фигур + расположение — строки по близости `top`)
  → материалы проекта: репозиторий (зеркало по SSH или локальный путь) и/или
    загруженные файлы (в т.ч. ZIP — распаковывается) — независимо друг от
    друга, вместе объединяются в один снимок (см. ниже)
  → matcher: единый агент, ОДНА сессия на весь план, по одному пункту за
    раз — модель сама выделяет пункт из текста слайдов (read_slides даёт
    посмотреть презентацию ещё раз), инструментами (list_files/read_file/
    search, без ограничения на число вызовов) проверяет его по коду, затем
    вызывает submit_verdict — пункт и вердикт (DONE/PARTIAL/NOT_STARTED/
    UNCLEAR) + evidence проверяются кодом сразу же, не дожидаясь конца
    сессии — и переходит к следующему пункту, пока не вызовет finish
  → проверка каждой evidence-ссылки по коду (путь, строка, якорь рядом)
  → «сделано сверх плана»: код, не процитированный ни одним пунктом
  → reporter: связный вывод по итогам всех пунктов сразу (необязательно)
  → CLI пишет на диск (progress_report.html, progress_model.json);
    веб отдаёт то же самое иначе — живой прогресс по SSE, затем JSON с
    итогами на GET /api/analyses/{id} (рисует frontend-web, не HTML с бэкенда)
```

Репозиторий — не единственный законный источник evidence, а один из двух,
которые можно объединять: `ToolBox` (агентные инструменты) и `extract_all`
(детерминированные экстракторы) трогают только `.files`/`.read(path)` —
ни разу не обращаются к git напрямую (`extractors/base.py::FileTree`). Веб
пользуется этим прямо: `progress/local_source.py::LocalTree` — тот же
контракт для загруженных файлов/ZIP, `CombinedTree` — то же самое поверх
git-дерева, когда заполнены оба поля формы. Матчеру и экстракторам после
сборки снимка физически всё равно, что за ним стоит — правка коснулась
только сборки снимка, ни агента, ни `ToolBox` трогать не пришлось.

Презентации описывают бизнес-идеи, а не код — заранее собранный список
кандидатов почти никогда лексически не пересекается с этим языком. Поэтому
`matcher` не разбирает готовый список фактов, а сам ищет инструментами
(`progress/agent_tools.py`) — тот же принцип, что у человека, впервые
открывшего незнакомый репозиторий: посмотреть структуру, погрепать по
ключевым словам, прочитать найденное, свериться с заданием ещё раз. Одна
сессия на весь план, а не отдельный изолированный цикл на каждый пункт с
собственным бюджетом, — осознанный компромисс: общий бюджет шагов и общая
история вместо изоляции по пунктам, зато один и тот же агент от начала до
конца, а не нетулованная роль planner отдельно от агентной роли matcher.
Пункт-за-пунктом через `submit_verdict` (а не один большой ответ в конце)
даёт устойчивость к обрыву: если бюджет шагов кончится до `finish`, в отчёт
всё равно попадут уже отправленные и проверенные пункты.

CLI (`cmd_progress`) и веб (`web/app.py`) зовут один и тот же
`progress/pipeline.py::run_progress` — поведение двух интерфейсов не может
разойтись.

Четыре правила:

1. **Клон только на чтение.** Мутирующие git-команды разрешены единственному
   модулю `pko/git/remote.py`. `pko/git/repo.py` allowlist'ит подкоманды —
   `checkout`/`reset`/`push` упадут до запуска git. Инструменты агента
   (`read_slides`/`list_files`/`read_file`/`search`) физически не могут ничего
   изменить — среди них нет ни одной пишущей операции; `submit_verdict`/
   `finish` тоже не пишущие — это управление ходом самой сессии, не репозиторием.
2. **Ссылка на код без проверки не публикуется.** Каждая evidence-ссылка,
   которую предлагает matcher, проверяется структурно
   (`pko/progress/verify.py`): путь и строка должны существовать на этом
   коммите, а рядом — слово из основания. Неподтверждённая ссылка в отчёт не
   попадает вовсе, но вердикт из-за этого не роняется — сам факт проверки
   в HTML не показывается (см. `render/progress_report.py`), решает только
   код, что вообще может попасть на страницу.
3. **Свободный текст тоже проверяется, не только структурные поля.**
   И объяснение matcher'а (`matcher._guard_explanation`), и сводный вывод
   reporter'а идут через `report/guard.check_text` — упоминание пути,
   которого нет в репозитории (или, у reporter'а, среди уже подтверждённой
   evidence), отклоняет текст целиком, не трогая сам вердикт.
4. **LLM предлагает, код проверяет.** `matcher` (номера слайдов, evidence) и
   `reporter` (пути в тексте) обязаны ссылаться только на
   реально переданные им данные — всё остальное отбрасывается кодом, а не
   принимается на слово.

## Проверка

```bash
make test          # PYTHONPATH=backend python3 -m unittest discover -s tests
make test-report    # то же самое + reports/TESTS.txt и reports/junit.xml
```

Тестовый репозиторий (`tests/fixtures/mini_repo`) создаётся автоматически при
первом обращении. `tests/test_progress_local_source.py` проверяет
`LocalTree`/`CombinedTree` отдельно от веб-слоя: zip-slip отклоняется,
лимиты размера/числа файлов работают, `ToolBox` читает загруженные файлы
так же, как git-дерево. Тесты веб-слоя (`tests/test_web_analyses.py`) используют
`fastapi.testclient.TestClient` — реальный порт не занимают, `frontend-web`
для них не нужен вовсе (это отдельный процесс, тесты ходят напрямую в FastAPI
app). Два теста (сквозные прогоны CLI и веб) читают настоящий собранный
`frontend-app/dist/index.html` — без него упадут с той же понятной ошибкой,
что и сам `pko` в рантайме; остальные тесты дашборда-пути подменяют сборку
и от неё не зависят.

Геометрия шеврона проверяется отдельно, на стороне JS — своя копия теста в
каждом из двух фронтендов (`frontend-app/src/chevron-geometry.test.ts`,
`frontend-web/src/components/dashboard/chevron-geometry.test.ts`):

```bash
cd frontend-app && npm test
cd frontend-web && npm test
```

## Границы

- Разбирается Python (FastAPI и т.п.), `pyproject.toml`, `requirements*.txt`,
  `package.json`, YAML/TOML/INI, `.env*`, CODEOWNERS — тот же периметр, что и
  у детерминированных экстракторов. Фронтенд целевого репозитория статически
  не разбирается.
- PPTX-план предполагается текстовым (карточки задач и таймлайн как нативные
  фигуры PowerPoint), не скриншотами: OCR/vision не реализованы.
- «Сделано сверх плана» — детерминированный кандидат (код без подтверждённой
  evidence ни у одного пункта плана), не вердикт модели: решить, действительно
  ли это дополнительная работа, должен человек, читающий отчёт.
- `pko serve` — без аутентификации и без HTTPS: для общего/многопользовательского
  сервиса нужен отдельный контур (обратный прокси, auth), сейчас не реализован.
- Загруженные файлы/ZIP (`progress/local_source.py`) читаются как текст
  (UTF-8, нечитаемое — заменяющими символами, как и содержимое git-объектов
  сегодня) — годится для кода, `.json/.csv/.yaml/.md/.ipynb` и подобного, но
  не даёт осмысленного текста из `.xlsx`/PDF-отчётов: для них нужен отдельный
  текстовый экстрактор, которого пока нет. Лимиты — 5000 файлов и 200 МБ
  суммарно на один анализ (`MAX_WORKSPACE_FILES`/`MAX_WORKSPACE_BYTES`).
