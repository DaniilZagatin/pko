# PKO progress

Сравнивает PPTX-план команды (карточки задач, таймлайн-схема по этапам) с
кодом целевого репозитория и выпускает отчёт о прогрессе: что сделано, что
частично, что не начато, что сделано сверх плана.

## Структура репозитория

```
backend/pko/    — весь Python-код: пайплайн, CLI, веб-эндпоинт (FastAPI)
frontend/       — одна самодостаточная HTML-страница веб-интерфейса
tests/
```

`backend`/`frontend` — раздельные каталоги верхнего уровня, а не фронтенд
внутри пакета: страница не Python package data, `pip install` пакета её не
затрагивает. `backend/pko/web/app.py` находит `frontend/index.html` по пути
относительно корня репозитория.

## Запуск

```bash
pip install -e .

# веб-интерфейс: http://127.0.0.1:8000 — файл плана, ссылка на репозиторий,
# результат в окне на странице
python3 -m pko.cli serve

# CLI, план + уже существующий локальный клон целевого репозитория
python3 -m pko.cli progress plan.pptx --repo-path ~/src/<repo>

# CLI, план + репозиторий по SSH-ссылке (клонируется зеркалом, read-only)
python3 -m pko.cli progress plan.pptx \
  ssh://git@<host>:7999/<project>/<repo>.git
```

Без `pip install -e .` (или вместо неё) — `PYTHONPATH=backend python3 -m pko.cli ...`.

`pko serve` — локальный инструмент: сервер слушает `127.0.0.1` по умолчанию,
не `0.0.0.0` — не рассчитан на доступ с других машин. Поле «репозиторий» в
веб-форме принимает и SSH-ссылку, и локальный путь (автоопределение).

Полезные флаги `progress`: `--branch`, `--out` (каталог отчёта, по умолчанию
`pko-progress-out/`), `--no-fetch` (не обновлять зеркало). У `serve`:
`--host`, `--port`.

## LLM-доступ

Нужны две роли — `planner` (текст слайдов → пункты плана) и `matcher` (пункт
плана + код → вердикт). Эндпоинт — любой OpenAI-совместимый (`/chat/completions`).
По умолчанию обе роли используют одни и те же переменные:

```bash
export PKO_ASSEMBLER_BASE_URL=...   # например, внутренний GLM-совместимый endpoint
export PKO_ASSEMBLER_MODEL=GLM-5.2
export PKO_ASSEMBLER_API_KEY=...
```

Если ролям нужны разные модели — `PKO_PLANNER_*`/`PKO_MATCHER_*` переопределяют
общий дефолт по отдельности. Без настроенного доступа и CLI, и веб
останавливаются до анализа с понятной причиной, а не собирают пустой отчёт;
после смены переменных `pko serve` нужно перезапустить, чтобы он их подхватил.

Ответы кешируются в `~/.pko/llm-cache` по (endpoint, промпт), температура 0.

## Как устроено

```
PPTX-план
  → чтение слайдов (текст фигур + расположение — карточки vs таймлайн)
  → planner: LLM → пункты плана (JSON, заземлён на реальные номера слайдов)
  → целевой репозиторий → зеркало по SSH (read-only) или локальный путь
  → детерминированные экстракторы → кандидаты кода
  → matcher: LLM → вердикт (DONE/PARTIAL/NOT_STARTED/UNCLEAR) + evidence на пункт
  → проверка каждой evidence-ссылки по коду (путь, строка, якорь рядом)
  → «сделано сверх плана»: код, не процитированный ни одним пунктом
  → отчёт (progress_report.html, progress_model.json) — CLI пишет на диск,
    веб отдаёт тот же HTML прямо в ответе
```

CLI (`cmd_progress`) и веб (`web/app.py`) зовут один и тот же
`progress/pipeline.py::run_progress` — поведение двух интерфейсов не может
разойтись.

Четыре правила:

1. **Клон только на чтение.** Мутирующие git-команды разрешены единственному
   модулю `pko/git/remote.py`. `pko/git/repo.py` allowlist'ит подкоманды —
   `checkout`/`reset`/`push` упадут до запуска git.
2. **Ссылка на код без проверки не публикуется.** Каждая evidence-ссылка,
   которую предлагает matcher, проверяется структурно
   (`pko/progress/verify.py`): путь и строка должны существовать на этом
   коммите, а рядом — слово из основания. Неподтверждённая ссылка не
   отбрасывается, но остаётся в отчёте помеченной как непроверенная, а вердикт
   `DONE`/`PARTIAL` без единой подтверждённой ссылки отчёт явно называет
   негрунтованным.
3. **Свободный текст тоже проверяется, не только структурные поля.**
   Текстовое обоснование matcher'а идёт через `report/guard.check_text`
   (`matcher._guard_explanation`) — упоминание пути, которого нет в
   репозитории, заменяет объяснение нейтральной пометкой, не трогая сам
   вердикт и evidence.
4. **LLM предлагает, код проверяет.** И `planner` (номера слайдов), и
   `matcher` (evidence) обязаны ссылаться только на реально переданные им
   данные — всё остальное отбрасывается кодом, а не принимается на слово.

## Проверка

```bash
make test          # PYTHONPATH=backend python3 -m unittest discover -s tests
make test-report    # то же самое + reports/TESTS.txt и reports/junit.xml
```

Тестовый репозиторий (`tests/fixtures/mini_repo`) создаётся автоматически при
первом обращении. Тесты веб-слоя (`tests/test_web_app.py`) используют
`fastapi.testclient.TestClient` — реальный порт не занимают.

## Границы

- Разбирается Python (FastAPI и т.п.), `pyproject.toml`, `requirements*.txt`,
  `package.json`, YAML/TOML/INI, `.env*`, CODEOWNERS — тот же периметр, что и
  у детерминированных экстракторов. Фронтенд целевого репозитория статически
  не разбирается.
- PPTX-план предполагается текстовым (карточки задач и таймлайн как нативные
  фигуры PowerPoint), не скриншотами: OCR/vision не реализованы.
- «Сделано сверх плана» — детерминированный кандидат (код без подтверждённой
  evidence ни у одного пункта плана), не вердикт модели: решить, действительно
  ли это дополнительная работа, должен человек, читающий отчёт.
- `pko serve` — без аутентификации и без HTTPS: для общего/многопользовательского
  сервиса нужен отдельный контур (обратный прокси, auth), сейчас не реализован.
