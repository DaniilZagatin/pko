# Первый запуск PKO

Эта инструкция проводит первый анализ внутреннего Bitbucket-репозитория по SSH.
PKO клонирует зеркало от имени текущего пользователя через его `ssh-agent`, читает
код и готовый JUnit XML, но не запускает код или тесты анализируемого проекта.

## 1. Проверить окружение

Нужны Python 3.11+, `git`, доступ во внутреннюю сеть и SSH-ключ с правами чтения
репозитория.

```bash
cd /Users/jlocehok/pko
python3 --version
git --version
ssh-add -l
ssh -T -p 7999 git@<bitbucket-host>
```

Если `ssh-add -l` не видит ключ, добавьте его в агент, например:

```bash
ssh-add ~/.ssh/id_rsa
```

При первом подключении сначала сверьте отпечаток Bitbucket с опубликованным внутри
компании, затем добавьте хост в `known_hosts`. PKO использует строгую проверку
хоста и не покажет интерактивный запрос пароля или подтверждения ключа.

## 2. Проверить историю без анализа

Возьмите SSH-ссылку из Bitbucket в формате
`ssh://git@<bitbucket-host>:7999/<project>/<repo>.git` и выполните:

```bash
PYTHONPATH=src python3 -m pko.cli history \
  ssh://git@<bitbucket-host>:7999/<project>/<repo>.git \
  --max-versions 6
```

Команда создаст или обновит зеркало в `~/.pko/repos/`, определит основную ветку и
покажет точки истории. PKO берёт начальный коммит с анализируемым кодом, текущий
коммит и до заданного лимита равномерно выбранные объединённые pull request или
merge-коммиты между ними. Если нужна другая ветка, добавьте `--branch <имя>`.

Перед продолжением проверьте, что репозиторий, ветка, первый коммит и последние
слияния определены правдоподобно. Повторный запуск можно выполнить без сети,
добавив `--no-fetch`.

## 3. Получить первый черновик

```bash
PYTHONPATH=src python3 -m pko.cli analyze \
  ssh://git@<bitbucket-host>:7999/<project>/<repo>.git \
  --max-versions 2 \
  --no-fetch \
  --out pko-out
```

Без заполненного `business_intent.yaml` ожидается статус `NO_DECISION` и код
возврата `4`. Это не ошибка запуска и не отказ в допуске: PKO намеренно не выводит
из кода потребность, владельца и целевое состояние.

В `pko-out/` сначала проверьте:

- `taxonomy.html` — найденные объекты и долю разобранных файлов;
- `passports.html` — паспорта и поле «Собран из кандидатов»;
- `gate_card-*.md` — основные проверки BASIC и причины статуса;
- `diff_*.md` и `comparison_*.html` — изменение от начальной к текущей версии;
- `pko_*.json` — машинную модель, если нужно разобрать спорный вывод.

Ссылки-доказательства содержат только путь, строку и краткое основание, без текста
исходного кода.

## 4. Подтвердить бизнес-контекст

Скопируйте образец в анализируемый репозиторий, заполните его вместе с владельцем
системы и закоммитьте рядом с кодом:

```bash
cp examples/business_intent.yaml \
  /path/to/analyzed-repo/business_intent.yaml
```

Обязательные поля: `confirmed_need_id`, `business_owner`, `target_state` и
`success_criteria`. Значения полей `requested_mode`, `maturity`, `consequence`,
`scale` и `decision_boundary` выбираются только из вариантов, перечисленных в
комментариях образца; опечатка приведёт к `NO_DECISION`, а не к более мягкому
профилю.

Если файл пока нельзя коммитить, передайте временный заполненный файл явно:

```bash
PYTHONPATH=src python3 -m pko.cli analyze \
  ssh://git@<bitbucket-host>:7999/<project>/<repo>.git \
  --max-versions 2 \
  --intent /path/to/business_intent.yaml \
  --out pko-out
```

Без JUnit XML после этого возможен `DENY` с кодом `3`: PKO видит ограничение в
коде, но не считает его поведение доказанным тестом.

## 5. Добавить готовый отчёт pytest

PKO не запускает тесты. Скачайте JUnit XML из CI для того же коммита, который
анализируется, и добавьте его к команде:

```bash
PYTHONPATH=src python3 -m pko.cli analyze \
  ssh://git@<bitbucket-host>:7999/<project>/<repo>.git \
  --max-versions 2 \
  --intent /path/to/business_intent.yaml \
  --junit /path/to/junit.xml \
  --out pko-out
```

JUnit применяется только к текущей версии. Доказательством считается пройденный
тест; пропущенный тест ограничение не подтверждает. Сопоставление делается по
именам тестов, поэтому в Gate Card нужно вручную проверить, что найденный тест
действительно проверяет указанное ограничение.

## 6. Подключить GLM и DeepSeek

Для первого сетевого прогона замените плейсхолдеры параметрами внутренних
OpenAI-совместимых endpoint'ов. Ключи передаются только через окружение:

```bash
export PKO_ASSEMBLER_BASE_URL='<GLM_BASE_URL>'
export PKO_ASSEMBLER_MODEL='<GLM_MODEL_ID>'
export PKO_ASSEMBLER_API_KEY='<GLM_API_KEY>'

export PKO_WRITER_BASE_URL='<DEEPSEEK_BASE_URL>'
export PKO_WRITER_MODEL='<DEEPSEEK_MODEL_ID>'
export PKO_WRITER_API_KEY='<DEEPSEEK_API_KEY>'

# Scout получает исходный код, поэтому его host должен быть разрешён явно.
export PKO_SCOUT_ALLOWED_HOSTS='<INTERNAL_GLM_HOST>'
```

Затем повторите полную команду из предыдущего шага с флагом `--llm`. GLM
группирует найденные кандидаты в объекты, а DeepSeek пишет русский обзор по уже
готовой модели и не получает исходный код. Решение Gate остаётся
детерминированным и не принимается языковой моделью. Если DeepSeek недоступен или
его текст не проходит проверку ссылок, PKO публикует шаблонный отчёт.

Для универсальной разведки кода добавьте `--agent`, `--scout-base-url`,
`--scout-model` и `--scout-api-key-env`. PKO сверит host endpoint'а с
`PKO_SCOUT_ALLOWED_HOSTS` до первого запроса; произвольный внешний URL будет
отклонён.

## 7. Прочитать результат

Код процесса означает:

| Код | Результат |
|---:|---|
| `0` | `ALLOW` или `ALLOW_WITH_RESTRICTIONS` — допуск выдан |
| `3` | `DENY` или требуется полный контур — допуска нет |
| `4` | `NO_DECISION` — не заполнен обязательный бизнес-контекст |
| `1` | ошибка доступа, клонирования или анализа |
| `2` | неверные параметры команды |

Ненулевой код `3` или `4` после успешно созданных отчётов — штатный результат
проверки, поэтому в первой ручной сессии ориентируйтесь и на код, и на файлы в
`pko-out/`.

Не используйте `--publish` до ручной проверки `pko-out/`: этот флаг заменяет
опубликованные отчёты в текущем каталоге или в `--publish-dir`, сохраняя прежние
версии с суффиксом `.bak`.

## Быстрая диагностика

- `Host key verification failed` — хост отсутствует в `known_hosts` или его
  отпечаток изменился; не обходите проверку, сначала сверьте отпечаток.
- `Permission denied (publickey)` — ключ не загружен в `ssh-agent` или у
  пользователя нет чтения репозитория.
- Не та ветка — повторите команды с `--branch <имя>`.
- Зеркало временно не обновляется — используйте `--no-fetch` только если нужные
  коммиты уже есть в кеше.
- В отчёте мало объектов — проверьте долю покрытия: первая версия анализирует
  Python/FastAPI/LangGraph и конфигурацию, но не разбирает TypeScript-фронтенд.
